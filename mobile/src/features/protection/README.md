# Protection (phone)

Phone-side protection from [plan 04](../../../../docs/plans/04-phone-protection.md), plus baseline findings 3 (Practice save privacy, N5), 4 (slow PIN hash, N4) and the https-only N-item from the [security baseline](../../../../docs/security/baseline-2026-11-22.md). Each protection has its own switch in `config.ts` (`PROTECTION`), so one can be turned off by an update if it misbehaves (the slow PIN hash and the fresh-install wipe are always on).

## What each protection does

| Protection | Switch | How it works | Where |
|---|---|---|---|
| App lock on by default | `lockByDefault` | Once an MPIN is on this phone (onboarding, the MPIN sheet, Settings), app lock turns on unless the person already chose on or off (`vw.appLock` is `"1"`/`"0"`; missing means "never chose"). Settings can still turn it off, with the MPIN. Whoever is in the app stays in; the lock applies from the next time. | `lib/auth/app-lock.ts` `applyLockDefault()`, `lib/session.ts`, `lib/auth/device-pin.ts` |
| Idle lock | `idleLock`, `IDLE_LOCK_MS` (5 min) | The root layout reports every touch (`onTouchStartCapture`) to `noteActivity()`; on the web, `watchAppLock()` listens for clicks and key presses on the page. Every 15 s the app checks: lock on, unlocked, app active, no system UI the app opened (camera, picker, Face ID) and 5 minutes since the last touch → it locks. Coming back to the app counts as a touch. The background lock and the Android system-UI and Settings-trip exceptions are unchanged. | `lib/auth/app-lock.ts`, `app/_layout.tsx` |
| App-switcher cover (iOS) | `appSwitcherCover`, `APP_SWITCHER_BLUR` | `PrivacyCover` keeps expo-screen-capture's native blur on all the time (app switcher, Control Center, calls), which also covers full-screen modals. In a build without the package it draws its own blurred cover while the app isn't active. Android: FLAG_SECURE blanks the switcher preview on the sensitive routes only (see the next row). | `PrivacyCover.tsx`, `lib/screen-capture.ts` `coverAppSwitcher()` |
| Screenshot blocking | `screenshotBlocking`, `SENSITIVE_ROUTES` | `SensitiveRouteGuard` reads `useSegments()` and holds the plan 02 adapter (`useSensitiveScreen`) while the route is one of: `withdraw`, `emergency-request`, `wallet/[action]`, `checkout`, `mpin`, `verify-id`, `recovery/claim`, `settings/security`, and every other screen with a PIN pad: `unlock`, `onboarding/pin`, `settings/reset-mpin`, `settings/trust-device`, `settings/limits`, `settings/delete-account`. Add a route to the list to cover it. A PIN pad inside a tab has no route of its own, so it holds the adapter itself: Invest's Core buy (`invest/core/LumpSumModal.tsx`, while it's open). | `SensitiveRouteGuard.tsx`, `routes.ts`, `invest/core/LumpSumModal.tsx` |
| Hide balances | `hideBalances`, `PEEK_MS` (30 s) | The eye next to "Safe in vaults" hides Home's amounts (the total, "added lately", vault cards and the wallet card) as `₹••••`; screen readers hear "Amount hidden". A tap on the hidden total shows them all for 30 s, or until the app leaves the foreground. Stored as `vw.hideBalances` (secure store); Delete account and sign-out clear it. The saved choice is read as the app starts, and until it's read the amounts count as hidden, so they never flash before the dots. Other screens (vault detail, wallet, activity) and Home's coming-up, insight and recent-activity amounts still show. | `balances.ts`, `HiddenAmount.tsx`, `home/Hero.tsx`, `home/VaultCarousel.tsx`, `wallet/WalletCard.tsx` |
| Root / jailbreak warning | `integrityWarning` | A warning banner on Home when `checkDeviceIntegrity()` (plan 02 adapter) says rooted; "Got it" hides it until the next launch. The web returns `null`, so it never shows there. It only warns, in Practice and live alike: **live builds could block money moves on such phones later; plan 08 decides.** | `IntegrityBanner.tsx`, `home/HomeScreen.tsx` |
| Session in secure storage | `secureSession` | Firebase's `getReactNativePersistence` gets an adapter over the secure store, with values split into 600-character chunks (`setSecureChunked` in `lib/storage.ts`) under the Keychain's size limit, keys made safe with `secureKeyFor("vwauth.", …)`. A write puts the new chunks in the other of two slots (`<key>_a.<i>` / `<key>_b.<i>`) and switches the head (`chunks:<slot>:<n>`) last, so a write cut short reads as the old value, never a mix; older `chunks:<n>` values still read. A session an older build kept in AsyncStorage (`firebase:*` keys) is copied over, and that copy wins over one already in the Keychain (it's the newer one, also after the switch is turned off and on); each key is deleted from AsyncStorage only once the Keychain gives the same value back, so a failed write signs nobody out. The web keeps `browserLocalPersistence`. The session's keys are listed apart from the `vw.*` index (`vw.chunkedKeys`), so an account wipe leaves them (Firebase removes them on sign-out). | `lib/auth/firebase.ts`, `lib/storage.ts` |
| Fresh install wipe (iOS) | always on | The Keychain outlives the app on iOS, so a reinstall would find the last install's session (its refresh token), PIN, lock and install id. A marker in AsyncStorage (`vw.install`, which goes with the app) tells a fresh install apart: missing with AsyncStorage empty means a fresh install, so the first storage call wipes every `vw.*` item and every listed session key before anything reads them; missing with something in AsyncStorage (the Practice save, an older build's `firebase:*` session) means an upgrade, and nothing is wiped. The marker is set to `"wiping"` first and read back (a marker that can't be kept never wipes), so a wipe cut short runs again. Android removes the secure store with the app, so it never wipes. | `lib/storage.ts` (`installReady`, `checkInstall`) |
| Biometric rules | `biometricRules` | Onboarding's protect step turns on Face ID / fingerprint unlock only when its check passes. If it doesn't, the person can try again or "Use my MPIN only" (`vw.bioUnlock` = `"0"`), and the Unlock screen then offers no biometric. Confirming "Turn on app lock" in Settings → Security with a passing biometric turns it back on; turning app lock off clears it. (A biometric never replaces the MPIN for changing it or turning lock off: plan 03, `SecurityFlow.tsx`.) | `lib/auth/app-lock.ts`, `account/onboarding/ProtectStep.tsx`, `account/UnlockScreen.tsx`, `account/settings/security/SecurityFlow.tsx` |
| Escalating wrong-PIN guard | `escalatingPinGuard` | Every device-PIN pad (Unlock, Security, Delete account): 4 free wrong tries ("Wrong MPIN. 3 tries left.", the MPIN sheet's words), then a wait after each wrong try in a row: 1, 5, 30, then 60 minutes. The 10th wrong try in a row: with a Firebase login on the phone, the app signs out of Vaultwise, in live and Practice alike (Practice can be the fallback while the server is out of reach, and a Practice "start over" alone would leave the live login behind an empty lock); Practice with nobody signed in, only "Start Practice over" carries on (clears Practice data and the phone's PIN, like Delete account in Practice, and signs out a login restored meanwhile); live without sign-in (prototype server), it keeps waiting 60 minutes. Each try is counted before the PIN is checked (cleared if it's right), so closing the app mid-check can't skip one. A wait never ends later than its full length from now, re-checked at launch and every second, so moving the clock back can't freeze it. A right PIN or a PIN change clears the count. Off: the old 5 tries then 30 s. | `pin-policy.ts`, `lockout.ts`, `account/pin-guard.ts`, `account/PinLayout.tsx` |
| Slow PIN hash | always on (not switchable: saved hashes depend on it) | The unlock PIN's verifier is PBKDF2-HMAC-SHA256 (`@noble/hashes`, pure JS) with a 16-byte random salt: `pbkdf2:<iterations>:<salt>:<hash>:<digits>`. Iterations are measured on each phone when a PIN is saved, to take about 300 ms (1,000 to 100,000), and stored with the hash, so `TARGET_MS`/`MIN_ITERATIONS`/`MAX_ITERATIONS` can be retuned without breaking saved PINs. Older single SHA-256 values keep working and are rewritten as PBKDF2 at the next right PIN. | `lib/auth/device-pin.ts` |
| Practice save privacy | always on | A `PracticeSlice` with `sensitive: true` is saved on its own in secure storage (`vw.practice.<key>`, through the chunked helpers, so a slice over one entry's ~2 KB still saves) instead of the AsyncStorage bulk save. A sensitive write counts as saved only once it has worked; a failed one is written again at the next save. The person's typed name and email and the names typed on vault members are the `person` slice (`demo/state.ts`; the bulk `state` slice keeps the sample name and blank member names); the Practice MPIN slice (`demo/mpin.ts`) and the devices slice (`demo/devices.ts`, the masked phone number) are sensitive too. The alerts inbox stays in the bulk save, so its words never carry the phone number or a typed payee (`demo/alerts.ts` `generaliseAlert` rewords older saves). Older saves still load (a sensitive slice found in the bulk save, or a plain value from before the chunks, is read and moved on the next write); the `FORMAT` envelope is the same; Delete account wipes the keys and their chunks with the other `vw.*` keys. | `lib/api/demo/persist.ts`, `lib/api/demo/state.ts`, `lib/api/demo/mpin.ts`, `lib/api/demo/alerts.ts` |
| https only | `httpsOnly` | The Data source screen refuses an `http://` server address unless `__DEV__` (a development build, for a server on the same network). The same check runs whenever the connection is applied (`initConnection`, `applyConnection`), so an `http://` address saved by an older build is replaced by the build's default address (`EXPO_PUBLIC_API_URL`, which comes with the build and isn't checked again). | `https.ts`, `account/settings/ConnectionScreen.tsx`, `lib/api/connection.ts` (`usableBaseUrl`) |

## Testing that needs a real phone

The web preview has no secure store, screen capture, root check or biometrics, so these need a development or store build:

- Screenshots and recordings are blocked on each `SENSITIVE_ROUTES` screen, and allowed again on Home.
- iOS: the app switcher shows the blur on every screen, including full-screen modals. Android: the recent-apps preview is blank on the sensitive routes.
- The app locks after 5 minutes without a touch, and not while the camera or photo picker is open.
- Signing in, killing the app and restarting the phone keeps the session; an install that was signed in with an older build stays signed in after the update (migration).
- iOS: sign in, delete the app, install it again: it opens signed out, with no PIN or lock, and Your devices lists it as a new device. Updating over an older build (signed in, or with Practice data) wipes nothing.
- Killing the app while it's checking a PIN counts the try; moving the phone's clock back during a wait doesn't make it longer than its full length.
- Screenshots are blocked on Unlock, onboarding's PIN step, Forgot your MPIN, Trust this phone, Limits, Delete account and Invest's Core buy.
- How long an unlock takes with the measured PBKDF2 count (look for about 0.3 s on a mid-range Android phone).
- A rooted Android phone or emulator shows the Home warning.
- Onboarding: cancelling Face ID at the protect step offers "Use my MPIN only", and then Unlock offers no Face ID.

## Known limits

- **Android app switcher outside the sensitive routes:** FLAG_SECURE is only set there, so Home's preview shows in recent apps unless "Hide balances" is on. Setting it app-wide would block every screenshot.
- **PBKDF2 is slow in pure JS on Hermes:** a phone gets roughly a few thousand iterations in 300 ms, not 100,000. The Keychain / Keystore is still the main protection for the verifier; a native PBKDF2 would allow far more.
- **The wrong-PIN wait still trusts the phone's clock going forward** (moving it ahead ends a wait early; moving it back can't stretch one), and the guard is on the phone only (the server has its own MPIN lock for money moves).
- **Fresh install wipe, upgrades:** an iOS upgrade from a build before the marker is told apart by what's in AsyncStorage. Someone signed in with an older build has its `firebase:*` session there, and Practice leaves its save there; someone who did neither has nothing there, so their phone is wiped once (PIN, lock, settings, install id) as if freshly installed. From this build on the marker is always set.
- **Practice save:** the masked email on a recovery claim, and payee names on Practice withdrawals and wallet payments, stay in the bulk save (the alerts no longer repeat them).
- **Tests:** `__tests__/protection.test.ts` covers `routes.ts`, `pin-policy.ts` and `https.ts` (Jest, `npm test`); the Practice save's damaged-save restore is covered in `lib/api/demo/__tests__/persist.test.ts`. Still untested: the chunk helpers (`splitChunks`, `parseChunkHead`, `chunkKey`) and `generaliseAlert`.
