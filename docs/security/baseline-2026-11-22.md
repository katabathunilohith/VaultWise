# Security baseline, 22 November 2026

> The "before" report for [plan 08](../plans/08-security-review.md). It records where Vaultwise stands before plans 03 to 07, so the final report can show what changed.

**Code measured:** commit `012a9fc`, plus the uncommitted work already in the tree when this review started (plan 01's Practice save and "Start Practice over", query-parameter validation, new tests). Changes from plans 02 to 07, which started on the same day, are left out. The full list is in the [checklist](masvs-checklist.md#what-this-measures).

## Summary

Vaultwise is a prototype, and every public build (the shared APK and the store build) is Practice only: pretend money, no calls to the Vaultwise server, and sign-in and ID checks switched off. So the real exposure today is small. Some foundations are sound: the server hashes PINs with scrypt, keeps ID numbers as an HMAC, verifies Firebase tokens properly, looks up every record by its owner and validates every request body. But most of what a money app needs is missing. Most money moves need no PIN on the server, PIN guesses aren't limited, app lock is optional and a biometric alone can get past it, nothing hides balances from screenshots or the app switcher, and a server started without sign-in is open to anyone. Against OWASP MASVS v2.1.0 the app scores **5 Pass, 9 Partial, 9 Fail and 1 N/A** across all 24 controls; on the 11 L1 controls it's **3 Pass, 6 Partial, 1 Fail, 1 N/A**. `npm audit` finds **1 critical and 7 high** packages in the server project and **4 high** in the phone app; the critical one (Next.js) is fixed by a patch-level upgrade, and none of the phone's highs are in the app bundle. Plans 03 to 05 close most of the gaps before the server goes online.

## MobSF scan

MobSF (Mobile Security Framework) is a free scanner that unpacks an APK and reports on its settings, code, permissions and libraries. It runs on your own computer.

### 1. Get the APK

Pick one:

- **Best: build the baseline commit.** Don't build from the main folder right now: EAS builds whatever is in the folder, uncommitted changes included, and plans 02 to 04 are changing it. Use a clean copy of `012a9fc` instead. It lacks only the uncommitted work (mainly plan 01's Practice save), none of which changes a setting MobSF reads.

  ```sh
  git worktree add ../vaultwise-baseline 012a9fc
  cd ../vaultwise-baseline/mobile
  npm ci
  npx eas-cli@latest login
  npm run build:apk
  ```

  `npm run build:apk` builds on Expo's servers (`eas build --profile apk --platform android`). When it finishes it prints a link; download the `.apk` from there. Afterwards remove the copy with `git worktree remove ../vaultwise-baseline`.

- **Quicker: the APK testers already have.** Download it from expo.dev → the Vaultwise project → Builds → the latest `apk` build. It is older than `012a9fc` (it predates over-the-air updates), so note that in the results.

### 2. Start MobSF

You need Docker Desktop installed and running. Then:

```sh
docker run -it --rm -p 8000:8000 opensecurity/mobile-security-framework-mobsf:latest
```

Open <http://localhost:8000>. If it asks you to sign in, the default user and password are both `mobsf` (from MobSF's own docs). `--rm` deletes the container and its scans when you stop it, so save the report before you close it.

### 3. Scan and save

1. Drag the `.apk` onto the MobSF page, or use **Upload & Analyze**. The static scan takes a few minutes.
2. On the results page, choose **PDF Report** in the left menu.
3. Save it as **`docs/security/mobsf-baseline.pdf`**.
4. Fill in [MobSF results](#mobsf-results) below.

### 4. What to look at first

MobSF reads the Android parts well, but the app's JavaScript ships as Hermes bytecode, which it can't read. Expect findings from React Native and Expo libraries; treat those as background unless they match a control.

| Look at | Expect | If not | Control |
|---|---|---|---|
| Manifest: `android:allowBackup` | `true` (finding N3) | Note it | STORAGE-2 |
| Manifest: cleartext traffic, network security config | Cleartext off | Real finding | NETWORK-1 |
| Manifest: `android:debuggable` | `false` | Real finding | RESILIENCE-4 |
| Manifest: exported activities, services, receivers | Only the launcher activity, plus library ones | List each extra one | PLATFORM-1 |
| App info: minimum and target SDK | 24 and 36 | Update CODE-1 | CODE-1 |
| Permissions | Camera, biometrics, internet, and a few added by libraries | Explain each extra dangerous one | PRIVACY-1 |
| Signer certificate | Signed by EAS with v2 or v3, not a debug key | Real finding | RESILIENCE-2 |
| Hardcoded secrets | Possibly the Firebase web API key (public by design) | Anything else is real | STORAGE-1 |
| Trackers | None | Explain each | PRIVACY-2 |
| Domains and URLs | `u.expo.dev`, Google and Firebase hosts | Explain each | NETWORK-1 |
| Shared library hardening (PIE, NX, stack canary, RELRO) | Mostly fine; flags come from React Native's native libraries | Background | CODE |

Then update every "confirm in MobSF" item in the [checklist](masvs-checklist.md).
