# Security overview

> Where Vaultwise stands today, ordered by risk, and which plan fixes each gap.

Sources: a code audit on 22 November 2026, plus findings made while writing the feature docs. Updated the same day after the server work for plans 03, 05, 06 and 07, and again after the fixes from four independent code reviews ([below](#security-review-2026-11-22)). Phone details are in [phone-security.md](features/phone-security.md). Every public build is Practice (pretend money, nothing sent to the server), so most of these matter once the server goes online in [plan 05](plans/05-server-online.md).

## Already in place

- **PINs** are stored hashed: scrypt on the server (`src/lib/users.ts`), salted SHA-256 on the phone.
- **MPIN on every money move** (server): `src/lib/money-routes.ts` lists every money action, and `requireMpin()` (`src/lib/mpin/verify.ts`) checks the PIN before any money transaction, with a lock that grows from 1 minute to 24 hours. See [mpin.md](features/mpin.md).
- **Devices and alerts** (server): a new device can move only small amounts for 24 hours, a signed-out device is refused, and security events raise an in-app alert and a push. With sign-in on, only the device that signs up is trusted at once. Signing a device out also ends every older sign-in except on trusted devices. See [devices-alerts-otp.md](features/devices-alerts-otp.md).
- **The phone number can't be used to take over the MPIN:** adding or replacing it needs the MPIN, replacing it needs a trusted device, and a new number can't reset the MPIN for 72 hours (`src/app/api/v1/me/phone/route.ts`, `assertPhoneSettled()` in `src/lib/otp/phone.ts`).
- **ID numbers** are kept as the last 4 characters plus an HMAC keyed with `IDENTITY_SECRET`. Rejected ID photos are deleted. The KYC steps flow keeps only names, year of birth, last 4 digits and an IFSC.
- **Sign-in tokens** (Firebase) are verified on the server with `jose` (`src/lib/auth/verify.ts`), and a token only goes to the server its login belongs to.
- **Production needs sign-in:** a production server without `FIREBASE_PROJECT_ID` refuses to start (`productionStartupProblem()` in `src/lib/auth/config.ts`, run by `src/instrumentation.ts`).
- **Web hardening:** security headers and a Content Security Policy in production (`next.config.ts`), a general rate limit per address and per person (`src/lib/rate-limit.ts`), and plain 500 answers with an error id (`src/lib/api.ts`). See [running-online.md](features/running-online.md).
- **Audit log:** every money move and decision is recorded in a hash-chained log (`src/lib/audit.ts`, `verifyAuditChain`).
- **Limits:** personal and per-market limits, an emergency safety pause, velocity rules and fraud flags.
- **Uploads** are checked for type, size and real image content, and limited to 20 per person per hour.
- **Consent:** nothing goes to the AI provider without the person's yes, on the phone and the web. The server treats a missing answer as no (`src/lib/ai-consent.ts`).
- **Store and APK builds** are Practice-only, so they never handle real money or real IDs.

## Security review, 2026-11-22

Four independent code reviews of the server and web app (the code stage of [plan 08](plans/08-security-review.md)) looked for ways round the plan 03 to 07 protections. Their findings, merged and grouped by area, and how each was fixed. Severity is for a live server with sign-in on; every public build is still Practice. Two more reviews looked at the phone app; their findings are in [Phone reviews](#phone-reviews) below.

## Rules for anyone changing the code

- Every route that moves money calls `customer({ money: "<action>" })` with a line in `src/lib/money-routes.ts`, and checks the body's `pin` with `requireMpin()` **before** any `tx()`. Money out also calls `assertDeviceMayMove()`. See [mpin.md](features/mpin.md).
- Write audit rows for failures **outside** the transaction that throws, or they vanish. `requireMpin()` enforces this for MPIN failures; do the same for anything new. The same goes for rate-limit counts.
- Don't hand-write error text for unexpected failures: throw, and `errorResponse()` hides the details behind an `errorId`. Throw an `HttpError` with a `code` for anything a client should act on.
- A new photo upload route calls `assertUploadsLeft(user.id)` right after `customer()`, and `limitUploads(user.id)` once the request is known to take the file, so only accepted uploads count.
- Never send personal data to the AI provider unless `aiConsented()` is true. `createProof()` requires `aiAllowed`; pass the route's `aiConsented()`. Never log ID numbers, PINs, codes or tokens.
- Anything that changes where texted codes go, or who can trust a device, checks the MPIN with `always: true`, so rollback mode can't skip it.
- Never show text from a URL the customer arrived with (such as DigiLocker's `errMessage`): map known codes to fixed sentences.
- On the server, root runs only the root-owned copies in `/usr/local/sbin`, never a file in `/opt/vaultwise`.
- Keep secrets in `.env.local` (on the server, `/etc/vaultwise.env`) only. Anything starting `EXPO_PUBLIC_` or `NEXT_PUBLIC_` is visible to anyone with the app.
- Before a release touching money or identity, re-read this page and run the [security review](plans/08-security-review.md) checks.

## Standards to measure against

- **OWASP MASVS** (Mobile Application Security Verification Standard), level L1 now, aiming for L2 once real money is involved.
- **RBI rules on authenticating digital payments** (in force since April 2026): two factors for every payment, one of them dynamic, such as possession of a registered device.
- **India's Digital Personal Data Protection Act 2023**: collect the least data, get consent, let people export and delete it.
